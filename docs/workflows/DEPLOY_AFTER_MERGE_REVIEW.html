Should deployments run only after a PR is merged?

Long image

A

Answer

Yes. Enforcing post-merge deployment only (P5) eliminates cross-worktree overrides and removes the need for a cross-worktree lease ledger.

  1. GitHub serializes every PR merge into origin/master, so each post-merge deploy includes all earlier merges.1
  2. Worktrees stay strictly edit-and-test sandboxes (P1 to P4), while $MAIN_ROOT becomes the sole deploy origin (P5).2
  3. All four 2026-11-03 override incidents in wahyz_omni came from unmerged or un-rebased worktree deploys.
  4. One invariant (CWD == $MAIN_ROOT and HEAD == origin/master) replaces multi-worktree lease tracking.3

How does post-merge deployment separate duties across P1–P5?

Diagram structure
  • Edit and test code edit
  • Deploy in worktree? block_wt
  • Merge PR to master pr_merge
  • Fast-forward main root ff_pull
  • Deploy STG then PROD deploy_stg
  • block_wt → pr_merge · blocked
  • edit → block_wt · P3 and P4
  • ff_pull → deploy_stg · HEAD is master
  • pr_merge → ff_pull · linearized
  1. Edit and test code ↗

    Run code edits, unit tests, static analysis, and PR CI checks inside .worktrees/<slug> during P1 through P4.

  2. Deploy in worktree? ↗

    PreToolUse hook denies firebase deploy, gcloud run deploy, and deploy_web.sh inside any linked worktree.

  3. Merge PR to master ↗

    P5 rebases the worktree onto origin/master and merges the PR after CI passes.

  4. Fast-forward main root ↗

    worktree_land.sh pulls origin/master with --ff-only on $MAIN_ROOT and removes the worktree.

  5. Deploy STG then PROD ↗

    Run canonical deploy scripts from $MAIN_ROOT at HEAD == origin/master, verifying STG before PROD.
