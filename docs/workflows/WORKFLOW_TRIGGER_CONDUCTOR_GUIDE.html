How should Operational Signals and Feature Requests trigger an Aggregate Workflow of Skills and Hooks safely?

Long image

A

Answer

Pair a first-party standard-workflow orchestrator skill (INV) with a deterministic state-machine conductor tools/ci/workflow_conductor.mjs (DOM) and four lightweight hook back-edges (UserPromptSubmit, PreToolUse, PostToolUse, Stop).

  1. Route interactive prompts (UserPromptSubmit) and headless CLI / Cron triggers (workflow_conductor.mjs start) into one worktree-scoped state file (.workflow-state.json + LOOP_CONTRACT.md) instead of inflating always-on prose (CLAUDE.md, AGENTS.md, GEMINI.md).1
  2. Enforce a six-phase state machine (P0 INTAKE -> P1 SEEDED -> P2 PLANNED -> P3 BUILT -> P4 VERIFIED -> P5 SHIPPED/LANDED) where each phase activates only its target neighborhood of skills (W1-W8) and cannot advance until its deterministic CLI gate passes.2
  3. Treat untrusted operational payloads (such as customer issue text) strictly as data, hash-lock Protected Verification Files in LOOP_CONTRACT.md at P1, and default autonomous signal runs to --stop-at pr-opened so a human approves merge and deployment.3
  4. Enforce zero-token safety invariants via hook back-edges: block primary-checkout edits and gh pr merge --delete-branch in PreToolUse, and block session completion in Stop (verify_session_delta.sh) if @Tags, formatting, or LOOP_CONTRACT.md verification files are violated.4

How does the 6-Phase Conductor orchestrate skills, agents, and gates from trigger to landing?

Diagram structure
  • P0. Intake and Classify intake
  • P1. Isolate and Seed seedwt
  • P2. Plan and Arch Fit planfit
  • P3. 4-Pillar Build build4
  • P4. Review and Gates verify
  • P5. Ship and Land shipland
  • build4 → verify · 4 pillars complete
  • intake → seedwt · capabilityId resolved
  • planfit → build4 · plan approved
  • seedwt → planfit · LOOP_CONTRACT seeded
  • verify → build4 · gate or review fail
  • verify → shipland · all gates green
  1. P0. Intake and Classify (Read-Only) ↗

    Classify L3 signal (Priority 1-8) or feature request via linear, assist-customer-issue, firebase MCP, and codegraph; reject spam/duplicates and resolve capabilityId.

  2. P1. Isolate and Seed Contract ↗

    Run using-git-worktrees + seed_loop_contract.mjs to create .worktrees/<slug>, write LOOP_CONTRACT.md with all 4 pillars, and record SHA-256 hashes of Protected Verification Files in .workflow-state.json.

  3. P2. Plan and Architecture Fit ↗

    Run brainstorming, writing-plans, arch-check (clean-arch-guard), and archify; pause for human approval on new features or schema changes.

  4. P3. 4-Pillar Implementation ↗

    Execute (1) TDD code (flutter-tdd, firebase-ops, gen), (2) Usage Guide (render_usage_guides.js), (3) In-App Tutorial (TutorialFlowContract + onboarding), and (4) @Tags unit/contract tests.

  5. P4. Multi-Agent Review and Verify ↗

    Fan out code-reviewer, clean-arch-guard, test (ksm_test_suite.sh), and verify-app; require verify_session_delta.sh == 0 and quality_gates.mjs check --scope changed == 0.

  6. P5. Ship and Land Lifecycle ↗

    Run ship-and-land (worktree_land.sh): open PR linking GLO-<n>, watch CI checks, enqueue/merge without --delete-branch, fast-forward primary root, and prune MERGED_CLEAN worktrees.
